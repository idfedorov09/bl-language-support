# Участие в разработке Z8BL

## Ветки и pull request

**`dev` — разработка и цель обычных PR; `master` — релизы.** Создавайте рабочую
ветку от актуального `dev`. Не направляйте обычную разработку в `master`:
пуш туда может немедленно опубликовать расширение.

Перед правкой проверьте фактическую ветку и `git status`; сохраняйте чужие изменения.
Изменения должны быть сфокусированными, тексты интерфейса — по-русски; формат
существующего debug-вывода сохраняйте без необходимости его менять.

## Локальная разработка и проверки

Для всего набора инструментов используйте Node.js 22. Unit/corpus-тесты работают
на Node.js 20+, OpenSpec 1.13.1 требует Node.js не ниже 20.19.0.
У расширения нет отдельного шага компиляции: исходники — CommonJS.

```sh
npm test
npm run test:corpus -- ../pro.doczilla.clm
# Можно проверить несколько checkout'ов:
npm run test:corpus -- ../pro.doczilla.clm ../pro.doczilla.cloud
openspec validate --all --strict --no-interactive
```

Corpus читает локальные BL-исходники и проверяет индекс/навигацию; не запускает
Doczilla и не заменяет проверку расширения в VS Code. Unit-тесты используют
тестовый VS Code API. В отчёте разделяйте эти проверки и сценарии реального редактора.

GUID regressions находятся в `test/guid*.test.js`, renderer — в
`test/recordCardView.test.js`. Corpus проверяет также F12 и командные карточки
статических `records` и `static final guid`-констант, но через тот же mock API. Для отдельной согласованной
editor-проверки GUID change нужны F12/hover и обе ссылки hover после смены курсора,
Quick Pick (часть UUID/имя/класс, отмена, unknown), карточка/переходы,
Workspace.General, dirty refresh, видимые loading/results и keyboard tabs,
раздельные usages, подменю Z8BL, открытие карточки/использований вкладкой без
нового сплита и несколько checkout; task 4.2 до этого не закрывайте.

Для проверки в **Extension Development Host** из корня репозитория:

```sh
code --extensionDevelopmentPath=.
```

После правок перезапустите dev-хост или выполните **Developer: Reload Window**.
Для изменения `contributes.menus` проверяйте свежезапущенный dev-хост именно этого
checkout. В актуальном manifest — **BL: Найти GUID** и подменю **Z8BL**;
старые названия и плоское меню требуют проверки загруженной копии/manifest,
а не повторного изменения уже настроенного подменю. Совпадение версии `1.1.0`
не различает локальные сборки без version bump.
Обычная установленная копия обновляется только после повторной установки VSIX;
команды упаковки и установки — в [README](README.md).
Канал **BL Debug** и разбор ложных диагностик — в [AGENTS.md](AGENTS.md).
Проверку UI/браузера и реальные HTTP-запросы агенты не запускают без отдельного запроса.

## OpenSpec: текущее поведение и будущие изменения

В проекте используется CLI **OpenSpec 1.13.1**. Проверьте `openspec --version`.
Если CLI отсутствует, установите именно эту версию, а не `latest`:

```sh
npm install --global @fission-ai/openspec@1.13.1
openspec --version
```

Каталог уже инициализирован: повторный `init` для обычной работы не нужен.
Контекст и правила находятся в [openspec/config.yaml](openspec/config.yaml),
карта baseline и backlog — в [openspec/README.md](openspec/README.md).

- [openspec/specs/](openspec/specs/) — **подтверждённое текущее поведение** расширения.
- [openspec/changes/](openspec/changes/) — **планируемые изменения**: proposal, design,
  delta-specs и tasks. Их наличие не делает функцию готовой.
- После реализации и релевантных проверок согласуйте обновление main specs и
  архивирование change. Не синхронизируйте невыполненный backlog в baseline.

Шесть локальных официальных skills, сгенерированных OpenSpec 1.13.1,
находятся в [.agents/skills/](.agents/skills/):

| Skill | Назначение |
| --- | --- |
| `openspec-explore` | Исследование, без реализации |
| `openspec-propose` | Новое предложение и артефакты плана |
| `openspec-update-change` | Пересмотр существующего плана |
| `openspec-apply-change` | Реализация согласованного change |
| `openspec-sync-specs` | Перенос подтверждённых изменений в main specs |
| `openspec-archive-change` | Архивирование завершённого change |

Читайте соответствующий `SKILL.md` перед использованием workflow. **Планирование
не разрешает apply:** реализацию начинайте только по отдельному запросу после
представления артефактов. Инструкции skills не заменяют согласованный scope.
Будущие задачи реализации остаются незавершёнными до фактического выполнения.

## Содержание PR и репорт багов

В PR укажите цель и scope, затронутый OpenSpec change/capability, выполненные
проверки и непроверенные сценарии. Если поведение меняется, согласуйте код,
тесты и спецификации. Не включайте случайный version bump, артефакты VSIX,
сгенерированные логи или реальные секреты.

Используйте [шаблон PR](.github/pull_request_template.md) и
[шаблон бага](.github/ISSUE_TEMPLATE/bug_report.md). Для ошибки навигации приложите
минимальный BL-пример, путь и строку, вывод `bl.dumpDiagnostics` и `bl.analyzeLine`
для той же строки и фактическую цель перехода. Удалите из отчёта секреты и приватные данные.

## Релизы и SemVer

Текущая автоматизация — [.github/workflows/publish.yml](.github/workflows/publish.yml):
**push в `master` либо `workflow_dispatch` запускает публикацию** в исходном
репозитории `idfedorov09/bl-language-support`. Workflow выполняет `npm test`,
использует Node.js 22 и `@vscode/vsce@4.0.0`, публикует с секретом `VSCE_PAT`.
Это не dry run. Даже ручной запуск не безопасен для экспериментов; не нажимайте
его для проверки документации или упаковки.
[Отдельный test workflow](.github/workflows/test.yml) запускает тесты для push/PR
в `dev` и `master` на Node.js 20.

Критерии выбора версии:

| Изменение | SemVer |
| --- | --- |
| Несовместимые настройки, команды или пользовательские контракты; отказ от обещанной поддержки | **major** |
| Новые возможности, совместимые с прежним поведением | **minor** |
| Совместимые исправления, устранение ложных диагностик и улучшения производительности | **patch** |
| Только документация, планы OpenSpec или tooling без изменения поставляемого поведения | **Без bump**, если перепубликация не нужна |

Примеры от текущей `1.1.0`: исправление ложного `chain` — `1.1.1`;
совместимый completion или новый Request Workbench — `1.2.0`;
удаление `bl.goToCompiledJava` без совместимого пути или отказ от ранее
поддерживаемых версий VS Code — `2.0.0`. При minor/major младшие части обнуляются;
один релиз получает один номер по наиболее существенному изменению.
Если требуется перепубликация только ради README/упаковки, нужен новый patch
и отдельное согласование выпуска, а не повтор прежнего номера.

Не повышайте версию при каждом коммите или создании change. Если релиз
действительно запрошен, отдельно выберите increment по всему составу релиза;
не переиспользуйте уже опубликованную версию. Не считайте наличие версии в
`package.json` подтверждением её публикации.

Порядок **только для согласованного релиза**:

1. Сверьте актуальный `dev`, diff, готовность функций, main specs и выполненные
   проверки; составьте перечень изменений и ограничений.
2. Согласуйте новую версию. Выполните только выбранную команду:
   `npm version patch --no-git-tag-version`, `npm version minor --no-git-tag-version`
   **или** `npm version major --no-git-tag-version`. Проверьте итоговый diff manifest
   и lockfile, если он есть. Не создавайте tag автоматически.
3. Повторите `npm test`, релевантный corpus и OpenSpec validation; упакуйте VSIX
   закреплённым `@vscode/vsce@4.0.0` и проверьте состав поставки. Результаты UI-проверки
   укажите отдельно; если её не было, не утверждайте обратное.
4. Подготовьте переход `dev` → `master` и публикацию только с явным разрешением.
   Commit, push и запуск workflow требуют отдельного согласования; запрос на
   правку кода или version bump сам по себе не разрешает их.
5. После разрешённой публикации проверьте результат workflow и опубликованную
   версию. До этого сообщайте «подготовлено», а не «выпущено».
